## 四、P0：必须优先修复

### P0-01 库存人口损耗按帧向下取整

位置：`scripts/autoload/game_state.gd:326-423`，重点为 `:401-402`。

现状：`stored_population` 是整数，但代码每帧执行 `int(stored_population - total_loss)`。只要 `total_loss` 是任意正小数，就会立刻少 1 人。

已复现：库存 10 人、极寒区域、仅结算 `0.001` 游戏日后，库存变为 9 人。帧率越高，同一游戏时间内的损失次数越多。暴露人口使用另一种逐帧 `int(loss)`，小额损失又可能永远无法累计。

修复要求：

- 为库存损耗和暴露损耗分别维护可序列化的小数累计器，累计到整数后再扣人口；
- 同一总游戏时长在不同帧率或不同分步数量下得到一致结果；
- 存档并加载后不得丢失尚未达到 1 人的累计损耗。

验收测试：分别用 `1×1.0 天`、`10×0.1 天`、`1000×0.001 天` 结算同一初始状态，人口结果和累计余数一致。

### P0-02 全局效率按更新次数变化

位置：`scripts/simulation/entity_manager.gd:521-538`。

现状：极热、极冷及恢复状态每次更新固定增减 `0.01/0.02`，没有乘游戏天数 `p_dt`。

已复现：同样经过 1 游戏日，一次结算得到 `0.99`，十次结算得到 `0.90`。

修复要求：所有连续变化率按游戏时间积分；必要时将当前“每帧量”重新标定为“每日量”。

验收测试：多种分步方案的最终效率误差不超过明确的小容差，并覆盖 1x/2x/3x/5x。

### P0-03 原料、电力与科研产出不守恒

位置：

- `scripts/simulation/entity_manager.gd:573-618`
- `scripts/autoload/game_state.gd:235-310`

现状：

1. 建筑消耗调用 `consume()` 后忽略失败结果，原料为 0 仍可生产；审查实测藻类燃料为 0 时，满员藻电站仍产生 15 电力。
2. `power_ratio` 被乘到所有非电力产出，而不是只影响需要电力的建筑。一个缺电的庇护所可能让不耗电的人工矿场和农场一起停产。
3. 研究院、实验室和科学院由 `GameState` 单独结算科研，不检查其电力或食物消耗是否成功，也不复用建筑实际运行倍率。
4. 无工人的发电站仍按完整基础速率消耗燃料，因为消耗与工人数/实际出力脱节。

设计歧义：修复前需明确“电力”是即时流量、可库存能源，还是二者组合。当前实现同时将它视为全局流量比例和有上限的库存资源，规则不一致。

修复要求：

- 每座建筑先计算实际运行比例，再以同一比例原子化扣除输入并发放输出；
- 任一必要输入不足时，输出必须按可支付比例下降或停止，不得免费产出；
- 仅依赖电力的建筑受到缺电影响；不耗电建筑不得被全局误伤；
- 科研建筑复用同一运行结果，不建立第二套绕过能耗的结算；
- 资源不得因负数参数或失败消费反向增加。

### P0-04 脱水/减员后存在幽灵劳动力

位置：

- `scripts/simulation/decision_manager.gd:402-427`
- `scripts/simulation/entity_manager.gd:93-117`
- `scripts/simulation/entity_manager.gd:119-137`

现状：人口入库、饥荒和环境减员只减少 `population.total`，不撤销生育者或建筑工人。

已复现：100 人中有 20 名生育者和 5 名建筑工人，执行脱水后状态为活跃人口 1、库存 99、生育者 20、建筑工人 5，建筑仍按 5 人满额产出。

修复要求：始终维护以下不变量：

```text
breeders >= 0
assigned_workers_per_building >= 0
breeders + counted_building_workers <= active_population
stored_population <= valid_storage_capacity
```

脱水需要定义并实现明确的撤岗顺序；饥荒和灾害减员也必须按可解释规则从人口分组与岗位中扣除。存入人口的公共 API 不得默认从已被多个系统占用的人口中重复取人。

### P0-05 科研点池无法投入研究

位置：`scripts/simulation/tech_tree.gd:185-204`、`:242-282`；UI 位置为 `scenes/tech_tree/tech_tree.gd:39-48`、`:104-108`。

现状：未研究时产生的科研点进入 `research_points`；开始研究后只接收新产生的点数，池中旧点没有消费入口。取消研究又把已注入点数退回这个无法使用的池。

已复现：持有 100 基础科研点开始望远镜研究，操作成功后科研点仍为 100，研究进度仍为 0。Tooltip 却显示池中点数与研究需求的对比，造成它们可用的假象。

设计抉择：

- 若采用“科研点库存”模型，开始研究或逐帧研究时必须从池中合法注入；
- 若采用“研究期间实时产出”模型，应移除误导性的库存、退回和需求展示，或赋予库存明确用途。

验收测试必须覆盖研究前积累、开始、部分进度、取消、重新开始、多类型科研和完成后的剩余点数守恒。

### P0-06 建造失败仍扣资源且可产生孤立建筑

位置：`scripts/simulation/decision_manager.gd:333-399`。

现状：`execute_decision()` 在验证区域前先扣资源、写冷却和历史。区域为 `-1` 时随后失败；区域 ID 大于 71 或区域管理器为空时，还可能返回成功并创建无法注册到区域的建筑。

已复现：区域 `-1` 建造藻类采集场返回失败，铁矿仍从 200 降到 180。

修复要求：

- 所有前置、区域存在性、管理器可用性和资源检查在任何状态写入前完成；
- 扣费、建筑创建、区域注册作为一个事务，要么全部成功，要么全部不发生；
- `can_execute()` 和 `execute_decision()` 使用同一套完整校验，不能由调用方是否传入科技树来绕过科技门槛。

### P0-07 存档未完整恢复倍率和区域环境

位置：

- `scripts/autoload/game_state.gd:522-605`
- `scripts/simulation/planet_zones.gd:426-466`

现状：

- `to_dict()` 保存 `time_scale`，`from_dict()` 却只写入 `environment.time_scale`；`GameState.time_scale` 在 `reset()` 后保持 1x，下一帧还会覆盖环境倍率。
- 区域状态保存温度，但不保存 `radiation` 和 `light_intensity`。手动存档通常处于暂停状态，加载后它们会持续显示为 0，直到玩家恢复模拟。
- 自定义配置未随存档保存；同进程中可能继承上一个宇宙的缓存配置，重启后又回退默认配置。
- 模拟随机数状态和轨迹未保存，同一存档重复加载后不能得到可复现分支；需明确这是设计选择还是缺陷。

已复现：保存 5x 状态并恢复后，`GameState.time_scale == 1.0`，而暂时无效的 `environment.time_scale == 5.0`。

修复要求：

- 建立明确的存档 schema 版本并完整恢复所有会影响继续游戏或暂停 UI 的状态；
- 保存—加载—再保存后，关键模拟字段应等价；
- 旧存档字段缺失时使用显式兼容默认值；
- 加载错误不得部分覆盖当前游戏状态。

## 五、P1：核心功能完整性

### P1-01 区域资源禀赋没有参与生产

位置：`scripts/simulation/planet_zones.gd:7-14`、`scripts/simulation/entity_manager.gd:592-618`。

现状：铁、铜、稀有矿、肥沃度和藻类密度只用于生成、展示和存档。建筑产出只乘温度效率，不读取这些区域值，因此零藻类区域仍可正常采藻，贫矿区和富矿区产量相同，农场不受肥沃度影响。

修复要求：先明确这些值是产量系数还是可耗尽储量，再让对应建筑通过模拟层统一计算。验收时，两个除禀赋外完全相同的区域必须产生可预测的不同产量。

### P1-02 区域辐射无方向差异，暗面散射违反设计

位置：`scripts/simulation/planet_zones.gd:219-251`、`:276-309`。

现状：辐射仅按恒星质量和距离计算，没有乘区域法线与恒星方向，因此所有区域辐射相同，辐射热力图缺少区域意义。代码默认暗面散射为 25%，而 `docs/游戏设计文档.md` 要求背面仅有 5% 散射辐射。

修复要求：根据设计明确光照与辐射各自的直射、散射和遮挡公式，并分别测试向光区、晨昏区和背光区。

### P1-03 多项建筑和科技效果只有说明文字

涉及内容：

- 辐射屏蔽站没有降低区域辐射或建筑/人口损伤；
- 庇护所和深地庇护所只提供库存容量，没有实现说明中的区域保护；
- `observatory` 没有增强星图信息；
- `radiation_armor` 只解锁建筑，没有实现描述中的建筑抗性提升；
- `high_alloy` 没有提高耐久上限或抗性；
- `nuclear_fusion` 没有对应聚变建筑或能源效果。

位置：`scripts/simulation/tech_tree.gd:97-157`、`scripts/simulation/decision_manager.gd:107-154`、`scripts/simulation/entity_manager.gd:191-276`。

修复要求：每个对玩家宣称的效果必须有模拟层调用方、存档字段和目标测试；暂不实现的效果应在当前 UI 中明确标为规划或移除可购买入口。

### P1-04 星图“轨道预测”只是匀速直线外推

位置：`scenes/starmap/starmap_view.gd:367-385`。

现状：预测线逐步执行 `position += velocity * 0.25`，不计算任一天体引力，却被 UI 和 README 描述为短程轨道预测、长程混沌预测。

修复选择：

- 使用模拟层的非破坏性快照和固定子步进行真实预测；或
- 在原型阶段把 UI 准确标为“速度方向线性外推”，不得宣称轨道或混沌预测。

预测过程不得修改真实状态或消耗真实随机数序列。

### P1-05 时间倍率和帧率会改变物理结果

位置：`scripts/autoload/game_state.gd:185-231`、`scripts/simulation/three_body.gd:119-190`。

现状：倍率直接放大单次 RK4 的 `dt`。5x 不只是更快播放，也使用更大的积分步长；帧率变化同样改变积分分段和随机扰动次数，因此轨道与碰撞结果依赖设备和倍率。

修复要求：使用固定模拟步长、累积器和必要的最大子步数；显示倍率只控制每个真实秒推进多少个固定步骤。相同种子和操作下，不同渲染帧率/倍率推进同样游戏天数后应得到容差内一致的状态。

### P1-06 设置页大部分选项没有实际效果

位置：`scenes/main_menu/settings_screen.gd:8-27`、`:115-153`、`:193-232`，以及 `scripts/autoload/game_state.gd:169-182`。

现状：自动保存、教程、通知、质量、粒子、FPS、四类音量、失焦静音、鼠标灵敏度、反转 Y、边缘滚动等只读写 JSON，没有实际调用方。持久化的全屏和 VSync 也不会在启动时应用；全屏分支下点击应用不会更新 VSync。保存失败时界面仍打印“设置已应用并保存”。

修复要求：逐项接线或隐藏尚未实现的控件；所有持久化设置在启动时生效；保存方法返回并展示真实结果。自动存档测试必须使用唯一测试存档并只删除自己创建的文件。

### P1-07 返回主菜单后仍残留当前游戏状态

位置：`scenes/game/game_menu.gd:95-100`、`scenes/main_menu/settings_screen.gd:235-237`。

现状：暂停菜单的“主菜单”只切换场景，不重置或标记会话。之后从初始菜单进入设置，返回逻辑因 `GameState.game_started == true` 而错误进入暂停菜单。

设计抉择：明确“返回主菜单”是结束内存会话还是保留可恢复会话。无论选择哪种，设置返回目标都应记录入口上下文，而不是用 `game_started` 猜测。

### P1-08 存档同秒覆盖、校验和路径边界不足

位置：`scripts/autoload/save_manager.gd:116-170`、`:183-205`。

现状：

- 文件名时间戳精度只有秒；同一宇宙和同一存档名在一秒内保存会使用相同路径并覆盖旧档，与文档“同名不覆盖”冲突；
- 扫描只验证头部 JSON，不验证 `state` 是否为可加载结构，损坏存档仍可能显示在浏览器；
- `load_game()` 在调用 `from_dict()` 前缺少完整类型校验，错误可能发生在部分状态已重置之后；
- `delete_save(filepath)` 没有确认目标位于 `res://saves/` 且是 `.sav`；当前 UI 不暴露任意路径，但 API 本身存在越界删除风险；
- `delete_universe()` 忽略单个删除失败并仍返回成功。

修复要求：使用微秒/安全序列或冲突检测生成唯一名称；加载先完整解析验证再提交；所有加载/删除路径规范化后限制在存档目录内；批量删除准确汇报部分失败。

## 六、P2：一致性和交互细节

### P2-01 文档中的科技数量和建筑数值与代码冲突

现状：代码实际定义 19 个科技节点（4+6+6+2+1），但 README、开发文档、详细参考文档和迁移说明多处写为 17 个；开发文档的表格本身也实际列出 19 项。

`docs/游戏设计文档.md` 与代码至少存在以下成本差异：

| 项目 | 设计文档 | 当前代码 |
|---|---|---|
| 火力发电站 | 200 铁 + 100 铜 | 120 铁 + 40 铜 |
| 科学院 | 1500 铁 + 500 铜 + 100 稀有 | 800 铁 + 200 铜 + 50 稀有 |
| 深地庇护所 | 400 铁 + 100 铜 | 300 铁 + 60 铜 |
| 辐射屏蔽站 | 300 铁 + 20 稀有 | 250 铁 + 50 铜 + 20 稀有 |

修复要求：先由玩法来源确定正确数量和数值，再改代码或相关文档；不得仅为了对齐而猜测哪一方正确。旧“17 节点”存档迁移设计也需重新核对实际 ID 集合。

### P2-02 星体显示半径与碰撞半径不一致

位置：`scripts/simulation/three_body.gd:193-200`、`scenes/starmap/starmap_view.gd:245-253`。

### P2-03 声明的信号、自动存档等接口未接通

### P2-04 模态输入和周期重建存在交互细节问题

### P2-05 声明的最低 Godot 版本与项目特性不一致

## 七、建议新增的回归测试

为避免继续出现“全部现有测试通过但核心逻辑错误”的情况，建议按职责新增独立测试，而不是把所有断言塞进现有 UI 测试。

### 1. `simulation_invariants_test`

覆盖：

- 同游戏时长不同分步下的人口损耗、效率、政策变化一致；
- 人口、生育者、工人和库存容量不变量；
- 原料不足时无免费产出；
- 不耗电建筑不受无关缺电影响；
- 科研建筑遵守输入和运行倍率；
- 负数输入不能增加资源、人口或岗位。

### 2. `research_lifecycle_test`

覆盖研究前积累、开始、逐类型注入、取消、退回、重新开始、完成、存读档及科技效果接线。

### 3. `persistence_roundtrip_test`

保存前构造非默认倍率、暂停状态、区域光照/辐射、政策、部分人口损耗累计、部分科研进度和自定义配置；加载后逐字段比较，并完成保存、扫描、加载、删除一轮。测试只删除带唯一前缀且由本次测试创建的文件。

### 4. `construction_transaction_test`

覆盖无区域、负区域、越界区域、空区域管理器、科技未解锁、资源不足、注册失败和合法建造；所有失败场景必须保持资源、历史、冷却、建筑列表和区域列表完全不变。

### 5. `zone_economy_test`

覆盖资源禀赋、肥沃度、藻类密度、温度、辐射、屏蔽和庇护效果；使用固定种子或手工构造区域，避免随机地形让测试不稳定。

### 6. `physics_step_invariance_test`

复制同一初始天体状态，以不同渲染帧率和倍率推进相同游戏时间，比较位置、速度、碰撞状态和区域环境。预测测试必须证明不会修改真实模拟。

### 7. `settings_navigation_test`

覆盖设置写入失败提示、启动应用、全屏/VSync、主菜单与暂停菜单两种入口返回，以及退出当前局后不再误入暂停菜单。

### 8. `save_browser_modal_test`

覆盖确认层打开时的 Enter/Delete/Esc、唯一文件名、损坏存档过滤、目录外路径拒绝和批量删除部分失败。

## 八、推荐修复顺序

1. 先建立模拟不变量测试，修复 P0-01、P0-02 和 P0-04，保证人口与连续量不再依赖帧率。
2. 明确电力模型，修复 P0-03；所有生产和科研统一走一次建筑运行结算。
3. 明确科研点模型，修复 P0-05，并补齐研究生命周期测试。
4. 将建造改为事务式操作，修复 P0-06。
5. 建立存档 schema 和完整往返测试，修复 P0-07 与 P1-08。
6. 接通区域禀赋、辐射、庇护和科技效果，处理 P1-01 至 P1-03。
7. 固定模拟步长并替换或更名星图预测，处理 P1-04、P1-05。
8. 最后处理设置、导航、文档数据和其余 P2 细节。

每个阶段完成后必须运行：

```bash
godot --headless --path . --quit
godot --headless --path . --quit-after 120
```

并运行该阶段新增或受影响的目标测试。只有代码、文档、回归测试和实际交互结果一致时，才能将对应条目标记为“已修复”。
