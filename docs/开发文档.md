## 项目概述

《三体文明》是一款基于刘慈欣《三体》世界观的三维星际经营模拟游戏。玩家在乱纪元中建立文明，发展科技，应对三体世界的不稳定环境。

### 技术栈

- **引擎**: Godot 4.7
- **脚本语言**: 纯 GDScript
- **3D 渲染**: SubViewport + WorldEnvironment + Camera3D + 程序化 ShaderMaterial + OmniLight3D + ImmediateMesh + GPUParticles3D（星图）；2D 热力图手绘（区域浏览）
- **UI 系统**: Control 节点 + Theme + `_draw()` 手绘列表/图表
- **存档与设置**: JSON（开发期统一读写 `res://saves/` 与 `res://settings.json`）
- **物理**: Jolt Physics（星图交互预留）

> **历史**: 项目原为 Python/Pygame 实现（2026-04）。2026-07 完全重写迁移至 Godot 4。
> 重写完成度：模拟核心、共享 3D 天空/星图渲染、区域地表观测、知识演化、区域建造、政策、存档、难度/稳定纪元、首都选择、区域认知、跨区行动、前哨/迁都，以及区域环境危机第一版纵向闭环已完成。技术效果后端继续服务当前生产系统，不承担旧格式转换。逐区域生产事务、电网/储能、对象级档案样机、途中改道、断供事件、科技终局与发布打包仍待实现。

### 开发期兼容政策

- 当前项目未发布，存档、设置、配置与数据资源只接受当前唯一格式；存档 `schema_version` 必须精确等于代码中的 `SAVE_SCHEMA_VERSION`。
- 结构变化时直接提升格式版本并重建开发测试数据。不得增加逐版迁移器、旧字段别名、缺字段推导、旧新字段双写或“临时”兼容状态源。
- 重构替换的字段、入口、适配器、测试和文档应在同一改动中删除。活动中的运行后端按现行职责保留并命名，不能仅因它来自早期原型就误标成兼容层。
- 正式发布前若需要支持测试版或发行版旧数据，必须另行确定支持矩阵、截止版本与删除期限；在此之前不以兼容性约束内部架构。

## 场景导航流程

```
main.tscn (入口)
  └── InitialMenu （标题画面）
        ├── 开始游戏 → StartGameMenu
        │     ├── 新游戏（命名 + 自动初始存档）→ MainScreen
        │     ├── 继续游戏（最新存档）→ MainScreen
        │     └── 加载存档 → SaveBrowser（分组可选列表）→ MainScreen
        └── 设置 → SettingsScreen

MainScreen （游戏主界面）
  ├── 菜单 → GameMenu （暂停菜单）
  │     ├── 继续 → MainScreen
  │     ├── 保存
  │     ├── 加载 → SaveBrowser（与主菜单相同）→ MainScreen
  │     ├── 设置 → SettingsScreen
  │     └── 返回主菜单 → InitialMenu
  ├── 科技树 → TechTreeScreen
  ├── 政策 → DecisionScreen
  ├── 区域/建筑 → ZoneViewScreen
  ├── 星图 → StarmapView (3D SubViewport)
  └── [开发者模式] 开发者工具 → 人口 / 资源 / 科研点 / 全科技调试
```

`GlobalInputRouter` 以 `GameState.current_screen` 作为唯一游戏内返回路由键。`Esc` 在 MainScreen 暂停模拟并打开 GameMenu；在 GameMenu 恢复模拟并返回 MainScreen；在科技树、政策、区域和星图返回 MainScreen；知识政策返回知识树。设置界面按 `settings_return_scene` 返回调用方。建造、帮助、存档、开发者工具和引导控制弹层可见时，`Esc` 优先关闭弹层。

## 目标架构与分阶段状态

本节记录跨阶段实现边界。A、B、C、D 与 E 的核心闭环均已落地；各节明确列出的高级扩展仍保持原模块边界。阶段性结构变更只需产生当前格式，不保留旧存档读取路径。

当前跨系统的真实性缺口、优先级与验收边界集中记录在 [架构与真实性审查](架构与真实性审查.md)；新增政策、区域经济或人口系统前应先检查该文档的 P0/P1 项。

### A. 区域地表观测主页面（已实现）

目标是将 `main_screen.tscn` 从三块数据面板改为“区域天空 + 地表 + 边缘 HUD”。不在 `main_screen.gd` 中复制星图 shader 和天体坐标逻辑，先提取共享渲染层：

```
GameState / ThreeBodySimulation / PlanetZoneManager
                  │
                  ▼
CelestialViewRenderer（共享天体材质、日冕、光源、位置同步）
          ┌───────┴────────┐
          ▼                ▼
StarmapView           RegionObservationView
自由宇宙坐标相机       区域地平坐标相机 + 地面遮挡
```

已实现文件：

- `scripts/rendering/celestial_view_renderer.gd`：创建/更新恒星、行星、光源和共享环境，不持有模拟状态。
- `scenes/game/region_observation_view.tscn/.gd`：接收 `zone_id`，计算当地天顶/地平坐标并组合天空、地面和区域建筑视觉层。
- `scenes/game/region_observation_view.gd` 内的地表绘制与建筑视觉注册表按建筑状态增量更新。
- `main_screen.gd` 只负责区域选择、HUD 和导航；当前观察区存入 `GameState.observed_zone_id`。

关键变换：取区域中心法线 `up`，由经纬计算 `east/north`，对 `star.position - planet.position` 归一化后投影到该基底。`dot(direction, up) <= 0` 的天体位于地平线下，不应被天空相机看到。渲染层只消费只读快照，不能反向修改模拟位置。

HUD 重构时，资源/文明/环境数据改为稳定 Label 原地更新，避免重新引入每帧销毁控件的问题。区域选择只改变观察目标；迁都、人口调动和建造保持独立命令。

### B. 知识与科技演化系统（已实现）

现有 `TechTree` 是生产、建筑和三类科研吞吐量使用的技术效果后端。知识系统按认知、研究、教育和危机保存拆分职责，并通过 `technology_effect_ids` 把已应用知识同步到该后端；它不是旧存档输入源：

```
KnowledgeSystem（认知状态、传承、衰退、证据）
    ├── DiscoverySystem（自然观察、实验、事件与遗迹线索）
    ├── ResearchProjectSystem（研究人员/设施/材料/时间）
    ├── EngineeringProjectSystem（理论→样机→工艺→应用能力）
    ├── KnowledgeGraph（节点定义、分岔、跨领域依赖、可见性）
    ├── KnowledgePolicySystem（制度筹建、实施时滞、维护岗位与历史）
    ├── EducationSystem（教师、学生、课程、教学与师徒实践）
    ├── PreservationAllocator（未来对象级避难容量与保存清单规则）
    ├── EnvironmentalHazardSystem（当前区域暴露、响应姿态、单次危机报告）
    └── KnowledgeInheritance（按代保留与灾难冲击）
```

已实现文件与数据：

- `scripts/simulation/knowledge_graph.gd`：加载数据驱动节点与不可变 ID，计算直接后继和跨领域依赖。
- `scripts/simulation/knowledge_system.gd`：维护 `HIDDEN/RUMOR/INSIGHT/RESEARCHABLE/RESEARCHING/MASTERED/APPLIED/DEGRADED`。
- `scripts/simulation/discovery_system.gd`：接受观察、实验、生产、随机事件和遗迹来源，输出标准化线索/证据，不直接控制 UI。
- `scripts/simulation/research_project_system.gd`：管理并行研究槽、人员、设施、样本、数据和失败/部分成果。
- `scripts/simulation/engineering_project_system.gd`：管理样机、测试、工艺验证和能力标签。
- `scripts/simulation/knowledge_inheritance.gd`：按代处理教师、学徒、记录副本、实践和灾难造成的保留/衰退。
- `scripts/simulation/knowledge_policy_system.gd`：维护知识制度的能力前置、筹建进度、实施人员、持续维护岗位与政策历史；未完成筹建的制度不产生保留效果。
- `scripts/simulation/education_system.gd`：拥有课程可传授性、组织方式、师生比、能力/设施前置和投入级别规则；UI 只提交课程、方式与级别，教师、学生和课时由模拟层推导并由统一人口系统扣减。
- `scripts/simulation/preservation_allocator.gd`：读取避难设施的生命保障、干燥库位、体积、承重和能源等容量，生成可预览、可复现的保存分配方案；不得自行读取未来真实轨道来估算伤亡。
- `scripts/simulation/environmental_hazard_system.gd`：读取当前区域环境、区域人口和实际运行庇护容量，保存响应姿态、活动危机、区域损失余量和唯一完成报告；不接收未来轨道真值。
- `resources/knowledge/knowledge_nodes.json`：节点、领域、依赖、线索条件、实验、工程化和当前技术效果映射；完整知识图不再硬编码在 UI。
- 知识政策当前由 `knowledge_policy_system.gd` 维护稳定政策 ID、能力前置和状态；当政策数量增长时再拆为版本化数据文件。

所有外部来源统一通过命令式接口接入，例如：

- `KnowledgeSystem.apply_discovery(node_id, source_id, clue_strength, evidence)`
- `DiscoverySystem.record_observation(...)` / `record_experiment(...)` / `resolve_event_discovery(...)`
- `GameState.start_knowledge_research(node_id)`
- `GameState.start_knowledge_engineering(node_id, project_id)`
- `GameState.adopt_knowledge_policy(policy_id)`
- `GameState.start_teaching_strategy(node_id, method_id, intensity_id)`
- `preview_preservation_plan(plan, forecast_snapshot)`
- `apply_knowledge_shock(shock)`

随机事件系统只能调用这些入口。知识系统完成状态判定后发出 `knowledge_state_changed`、`branch_revealed`、`knowledge_degraded` 等信号，科技树 UI 订阅只读状态。这样可为大量未来事件和节点预留扩展空间，而无需让事件知道界面节点或研究点实现。

能力消费方通过稳定标签查询，例如 `has_capability("precision_optics")`、`get_capability_level("orbital_observation")`；建筑、星图预测和生产系统不得依赖科技中文名或 UI 可见性。

知识政策只能从知识图进入并返回知识图。界面向 `KnowledgePolicySystem` 提交制度筹建命令，向 `EducationSystem` 提交课程、组织方式和宏观投入级别；规则、人数、师生比、课时、设施和岗位机会成本全部由模拟层验证。教学计划有持久列表并可暂停、继续、取消。尚无实际分配器消费的总体/载体/领域权重不显示。当前危机界面向 `EnvironmentalHazardSystem` 提交人口/均衡/知识优先姿态，只显示实际运行庇护容量与文明公开预测；`PreservationAllocator` 保留为未来对象级装载规则后端，当前普通 UI 不允许手填虚构对象数量。`KnowledgeInheritance` 最终依据实际幸存者、设施损毁和响应姿态生成灾难冲击，禁止政策本身直接增加知识值。

第一版知识政策树只实现四条设计文档已经定义的分支：教育与教学、记录与复制、危机保存、灾后恢复。容量与装载计算必须是给定状态和方案即可复现的纯规则；同一份文明预测快照下反复比较方案不得重掷预测。真实灾害结果只在模拟推进中确定一次，既不能因切换方案重掷，也不能提前泄露给预览层。

### C. 开局难度与稳定纪元（已实现）

当前由 `ScenarioManager` 统一调度分阶段轨道提供者：

```
ScenarioManager
    ├── difficulty_id / stable_years / chaos_start_day / seed
    ├── ScenarioDifficultyConfig（开发期可编辑的难度预设目录）
    ├── StableEphemerisProvider（解析二体 + 两颗远星规定星历）
    └── ChaoticNBodyProvider（现有 ThreeBodySimulation RK4）

ObservationNetwork + SatelliteNetwork + KnowledgeSystem
                         │
                         ▼
HazardForecastService（文明可知的轨道情景、区域危害与伤亡/知识损失区间）
                         │
                         ▼
EnvironmentalHazardSystem / Crisis UI（当前真值只进结算，预测只进公开提示）
```

- `resources/configs/scenario_difficulty_config.gd`、`difficulty_preset.gd` 和唯一数据资源 `scenario_difficulties.tres` 已落地。默认 `easy=100`、`normal=50`、`hard=25`、`extreme=0` 以及自定义上下限都只写在该资源中，不在脚本、场景或 UI 再维护副本。
- 这是随项目提交的开发/平衡配置，不是 `settings.json`、游戏内开发者模式或玩家可修改选项。开发者可用 Godot Inspector 或文本编辑 `.tres`，修改后由配置测试统一校验。
- `StartGameMenu` 在宇宙命名后增加难度步骤；菜单从配置资源生成标准预设，自定义输入使用资源中的上下限校验后再创建游戏。
- `ScenarioManager.create_scenario()` 接收已经解析和校验的预设快照，而不是自行按 ID 查硬编码 `match`。新宇宙把 `difficulty_config_version`、`stable_years` 和 `chaos_start_day` 写入场景状态。
- `ScenarioManager.update(game_time)` 在稳定纪元提供连续位置/速度快照；到 `chaos_start_day` 时将同一快照交给 RK4 模拟器，设置一次性转换标志并发出事件。
- 稳定阶段环境系统仍消费天体快照，不关心快照来自规定星历还是 N 体积分。
- 碰撞检测、轨迹历史、星图与地表天空统一消费当前轨道提供者，禁止每个界面各自判断阶段。
- 新游戏生成时离线验证转换目标状态：稳定期无碰撞、行星围绕主恒星、远星在转换时形成可运行的多体初值；转换之后不再脚本化。
- 默认数据：简单 100 年、普通 50 年、困难 25 年、极限 0 年、自定义 N 年；1 年 = 365 游戏天。这里仅记录设计默认值，运行时唯一来源是 `scenario_difficulties.tres`。
- 配置热改只要求在下一次启动/重新加载项目后影响新游戏，不要求运行中的菜单热更新。已有存档永远使用自身场景快照，禁止加载时用最新预设覆盖。
- 配置资源无效时应阻止新游戏并报告重复 ID、负数/非有限年数、缺失默认项或非法自定义范围，不得用隐藏的脚本常量兜底。

轨道预测能力改为读取 `KnowledgeSystem` 的理论标签、`ObservationNetwork` 的数据质量和 `SatelliteNetwork` 的覆盖率。稳定期二体理论只提高理想轨道理解，不直接给予混沌预测；真实多体偏差出现后才能产生相应发现线索。

`scripts/simulation/hazard_forecast_service.gd` 已实现，职责是把文明已掌握的能力标签、带误差的观测数据、人口/建筑脆弱性资料和计算资源转换为版本化 `HazardForecastSnapshot`。其方法签名不接收 `ScenarioManager`、未来轨道、场景种子或灾害结算结果。

预测显示按能力标签逐步开放：`hazard_warning` 只提供定性风险，`regional_hazard_projection` 提供区域与宽时间窗，`casualty_estimation` 提供伤亡区间，`knowledge_loss_projection` 提供知识载体和节点退化风险。即使标签已解锁，缺少观测基线、仪器校准、卫星覆盖、计算能力或人口/建筑数据时也要降低精度并扩大置信区间。

必须保持两条数据流分离：玩家预览消费 `HazardForecastSnapshot`；灾害实际结算消费 `ScenarioManager` 推进后产生的真实 `HazardOutcome`。预览不得把真实结果传给 UI 再用遮罩隐藏，因为界面刷新、辅助功能或方案差分都可能泄露信息；未知字段应在预测服务输出中就不存在。

### D. 当前存档格式（schema 10 已实现）

顶层 `schema_version` 当前为 10，并且加载时只接受精确版本。当前格式保存：

- `observed_zone_id`
- `knowledge`、`research_projects`、`engineering_projects`、`discoveries`、`inheritance`
- `knowledge_policy`（运行制度、筹建进度与维护岗位）、`education`、`preservation_plan`

- `hazard_forecasts`（生成时间、输入数据版本、能力层级、情景区间、置信度和过期状态）
- `environmental_hazards`（响应预案、活动危机、区域损失余量、完成报告与知识损失向量）

### E. 起始定居、开局引导与区域扩张（核心闭环已实现）

`StartGameMenu` 已有 `MAIN/NAMING/DIFFICULTY/GUIDANCE`；创建世界与初始存档后由主页面完成第 0 天首都选择。教学逻辑没有堆叠在菜单，而是拆成以下职责：

```
StartGameMenu（命名 / 难度 / 引导模式 / 创建）
                        │
                        ▼
OpeningGuidanceController（可保存阶段机，只提交领域命令）
       ├── CapitalSelectionService（只读公开区域认知，确认发源地）
       ├── MainScreen GuidancePanel（任务卡、语义高亮、局内手册与暂缓/恢复）
       ├── ExplorationSystem（区域认知、勘探队、结果置信度）
       ├── SettlementSystem（前哨条件、聚落升级、首都身份切换）
       ├── RegionMovementSystem（人口组、路线、时间、暂停与到达）
       └── RegionalLogisticsSystem（区域库存、运输、网络与施工供给）
```

已实现：

- `scripts/simulation/capital_selection_service.gd`：基于文明公开数据生成/比较候选区；不得读取隐藏矿藏或未来轨道评分。
- `scripts/simulation/exploration_system.gd`：维护 `UNKNOWN/OBSERVED/FAMILIAR/SURVEYED/MONITORED` 与带置信度的认知快照。
- `scripts/simulation/region_movement_system.gd`：管理勘探、迁徙、运输与迁都队在 144 区邻接图上的路线、行程与暂停状态；迁移校验出发区实际闲置人口，UI 选择出发区和人数。
- `scripts/simulation/settlement_system.gd`：管理区域人口、前哨实际补给指标、升级条件与首都身份。
- `scripts/simulation/regional_logistics_system.gd`：管理区域库存、运输任务、道路/管线/电网连接和目标区域施工供给。
- `scripts/guidance/opening_guidance_controller.gd`：数据驱动任务状态机，只监听领域事件并请求合法命令，不直接增加资源、解锁科技或移动人口。
- `opening_guidance_controller.gd` 当前内置版本化稳定任务定义；外部任务资源可在任务数量增长后再拆分。
- `main_screen.tscn/.gd` 提供首都不可逆选择层、轻量任务卡、当前进度手册、主页语义控件高亮与整组暂缓/恢复；百科式内容与跨场景通用注册仍待扩展。

新游戏创建后先写入可恢复的初始存档，再进入第 0 天暂停的定居阶段。`OpeningGuidanceController` 在完整/精简/关闭三种模式下共享同一世界状态：关闭引导只隐藏讲解，仍必须完成首都选择。任务完成必须来自例如 `capital_confirmed`、`time_control_used`、`teaching_plan_progressed`、`construction_started`、`expedition_departed` 等真实结果信号；教学计划仅创建或单纯打开页面不算完成。

区域推荐和教学提示只消费 `ZoneKnowledgeView`。若两个场景的公开输入相同，即使隐藏矿藏或未来真实轨道不同，候选排序与提示也必须相同。指导层不得持有完整 `PlanetZone` 真值对象再在 UI 隐藏字段。

跨区系统以 `EntityManager` 资源作为文明唯一总账，区域与在途库存作为严格对账的空间分账；建设先检查并扣除地方分账，生产/日常消耗后再按建筑位置对账。人口从出发区进入行动状态，抵达前不会进入目标区。跨区成本由真实人员、口粮、载荷和时间产生，不保留固定 `3~5 倍` 惩罚。

引导状态随每个存档保存；设置只保存当前三态默认引导模式。当前格式缺少首都、区域人口/库存或引导状态时直接拒绝加载，不由全局状态或历史设置键推导。

## 模拟子系统详解

### 1. 三体运动模拟 — `scripts/simulation/three_body.gd`

`class_name ThreeBodySimulation extends RefCounted`

**功能**: 4 天体（3 恒星 + 1 行星）引力模拟，输出环境参数供其他模块消费。

**关键常量**:
- `G = 1.0` — 简化引力常数
- `TRAIL_LENGTH = 200` — 每星轨迹点数

**内部类 StarData**: 持有 mass / position / velocity / color / radius / is_planet / trail

**关键方法**:

| 方法 | 功能 |
|---|---|
| `_init()` | 随机生成层级稳定初始配置（内双星 + 外第三星 + 行星绕双星） |
| `compute_forces_for_state(positions)` | 遍历星对计算引力合力（用于 RK4 四步） |
| `update(dt)` | RK4 四阶积分 + 1e-5 随机微扰 + 轨迹 pop_front |
| `has_collision()` | 检查任意两天体中心距是否小于半径和 |
| `get_environment_params()` | 输出光照强度（归一化）/ 热等级 / 温度 / 辐射 / 稳定性 |
| `get_stars_data()` | 返回 [{position, mass, is_planet}, ...]（供区域系统） |
| `get_planet_position()` | 返回行星坐标 |

**环境参数公式**:
- 光照强度 = `clamp(Σ mass×10/(dist²+100) / 8, 0, 1)`
- 温度 = `-273.15 + total_intensity × 7000`
- 辐射 = `Σ mass×200 / dist^2.5`
- 稳定性 = `1 / (1 + 行星加速度/0.1)`

### 2. 行星区域系统 — `scripts/simulation/planet_zones.gd`

`class_name PlanetZoneManager extends RefCounted`

**功能**: 144 区域（12 经度 × 12 纬度）的自转、光照、温度、辐射模拟。

**关键常量**:
- 6 种地形: 平原 / 高原 / 山地 / 峡谷 / 盆地 / 丘陵
- `TERRAIN_RESOURCE_TABLE` — 地形→矿物/肥沃/藻类系数
- `TERRAIN_THERMAL_MODIFIER` — 地形默认温度修正（高原-6°C / 山地-10°C / 盆地+3°C）

**内部类 PlanetZone**: 除 zone_id / 地形 / 辐射 / 光照 / 资源禀赋 / 建筑列表 / 面积权重外，持有地表温度、近地气温、氮/氧气态比例。

**关键方法**:

| 方法 | 功能 |
|---|---|
| `_init(env_config)` | 初始化 144 区 + 构建邻居缓存 |
| `_init_zones()` | 按经纬划分 144 格，随机分配地形和资源（±30% 浮动） |
| `_build_neighbor_cache()` | 每区 ≤4 邻居（经纬相邻，经度环绕） |
| `update(dt, time_scale, stars_data, planet_pos)` | 更新自转角度 → 逐区环境计算 |
| `initialize_temperatures(stars_data, planet_pos)` | 只在开局建立参考辐照、校准 20℃ 均温并执行 12 天小步长气候旋转 |
| `_compute_zone_environments()` | 光照/辐射强迫 → 四次方根辐射平衡 → 地表—大气交换 → 双速率扩散 |
| `_update_atmospheric_phase()` | 按氮/氧参考相变温度渐进更新气态比，凝结后削弱输热和温室效应 |
| `get_average_environment()` | 返回面积加权的地表/气温、辐射、光照和大气质量比 |
| `get_zone(zone_id)` | 按 ID 返回 PlanetZone |
| `get_all_zones_summary()` | 返回 144 区简要数据列表（模拟层；公开 UI 另经区域认知裁剪） |
| `add_building_to_zone / remove_building_from_zone` | 维护区域-建筑关联 |
| `get_state() / load_state()` | 序列化 / 反序列化 |

**工作效率函数** (`_calc_work_efficiency`):
- -10°C ~ 40°C → 1.0（满分）
- < -80°C 或 > 100°C → 0.0（无法工作）
- 中间线性插值

### 3. 实体管理器 — `scripts/simulation/entity_manager.gd`

`class_name EntityManager extends RefCounted`

**功能**: 管理 7 种资源、所有建筑、人口增长/库存/食物消耗。

**三种内部类**:
- `GameResource` — 单种资源（name / amount / max_storage / add / consume）
- `PopulationManager` — 人口系统（total / breeders / stored_population / 增长 / 饥荒 / 库存操作）
- `GameBuilding` — 单个建筑（17 种类型，耐久 / 产出 / 消耗 / 建造进度 / 环境伤害）

**7 种资源**: 铁矿 / 铜矿 / 稀有矿物 / 藻类燃料 / 化石燃料 / 电力 / 食物

**关键方法**:

| 方法 | 功能 |
|---|---|
| `_init(config)` | 初始化资源池和人口（100 人起始） |
| `add_building(building)` | 添加建筑到列表 |
| `get_resource(name)` | 查资源量，"population" 转发到 PopulationManager |
| `consume_resource / produce_resource` | 资源存取 |
| `get_buildings_by_type(type)` | 筛选活跃同类型建筑（科研产出用） |
| `get_idle_population()` | 总人口 - 生育者 - 建筑工人 |
| `assign_worker_to_building / unassign_worker_from_building` | 工人分配 |
| `assign_breeders / unassign_breeders` | 生育分配 |
| `get_electricity_balance()` | 发电量 vs 耗电量 |
| `update(env_params, zone_manager, dt, dehydrated)` | 重算库存容量 → 原子化建筑运行结算 → 区域保护/环境伤害 → 建造进度 → 人口增长与撤岗校正 |
| `_process_buildings(dt, zone_manager, dehydrated)` | 计算各建筑实际运行比例 → 结算燃料与即时电网 → 按同一比例发放产出并记录科研设施运行率 |
| `get_state() / load_state()` | 全量序列化（含所有建筑详情） |

**建筑产出公式**: `满岗产出 × 工人填充率 × 耐久率 × 温度效率 × 区域禀赋系数 × 必要输入可支付率 ×（仅用电建筑）供电率 × 政策/自动化倍率`

**人口增长公式**: `breeders × base_growth_per_breeder × food_satisfaction + idle × natural_growth_rate × food_satisfaction`

| `_init(config)` | 从 config["technology"] 构建节点（无 config 时用硬编码默认） |
| `produce_research(type, amount)` | 产出科技点 → 优先注入当前研究 → 剩余入池 → 检查完成 |
| `start_research(id, entities)` | 原子扣除物质资源 → 标记 researching → 按类型从库存科研点注入并检查完成 |
| `cancel_research()` | 退回已注入点数（物质不退还） |
| `can_start_research(id, entities)` | 检查前置科技/资源/人口/单研究限制 |
| `get_research_progress()` | 当前研究整体进度百分比 + 各类型明细 |
| `is_researchable(id)` | 前置已解锁且自身未解锁未研究中 |
| `get_state() / load_state()` | 解锁列表 + 研究进度 + 科技点数池 |

**科研产出来源**（在 GameState._process_research_output 中）:
- 人口自然产出 = `population / 500 × 天数`
- 研究院（research_institute）→ 基础科研 1.0/工人/天
- 实验室（laboratory）→ 应用科研 2.0/工人/天
- 科学院（academy）→ 理论科研 1.0/工人/天
- 脱水状态 × 0.1

`ResearchProjectSystem` 将“对应机构吞吐量 + 研究人员×0.04”的合计日工作率再乘以 `0.5`，项目管理界面的工作量/天和 ETA 使用同一实际速率。`EngineeringProjectSystem` 保持独立的工程化速率。

### 5. 决策管理器 — `scripts/simulation/decision_manager.gd`

`class_name DecisionManager extends RefCounted`

**功能**: 17 种建筑建造 + 三项当前可结算的文明应急命令。

**内部类 Decision**: 持有 id / category("construction"/"policy") / resource_cost / tech_requirement / worker_capacity / per_worker_output / build_time / storage_capacity...

**17 种建筑**: 藻类采集场 / 藻类采集与粗加工营地 / 铁矿场 / 铜矿场 / 稀有矿场 / 农场 / 化石燃料矿井 / 藻类发电站 / 化石燃料发电站 / 庇护所 / 实验室 / 科学院 / 深地庇护所 / 辐射屏蔽站 / 脱水仓 / 大型脱水仓 / 研究院。建造 UI 只列当前科技已允许的条目，不以禁用项剧透未来设施。

**关键方法**:

| 方法 | 功能 |
|---|---|
| `_init(config)` | 从 config["buildings"] 构建决策列表（无 config 用硬编码） |
| `get_construction_decisions()` | 返回所有建造类决策 |
| `get_policy_decisions()` | 返回全民脱水/浸泡复苏/应急定量配给 |
| `can_execute(id, entities, tech_tree, zone_manager, zone_id)` | 统一检查冷却、科技、资源、政策、区域和管理器有效性 |
| `execute_decision(id, entities, tech_tree, zone_manager, zone_id)` | 全部前置通过后事务式扣费、区域注册和实体提交，失败时不留状态 |
| `_execute_construction(decision, entities, zone_manager, zone_id)` | 创建 GameBuilding 实例（under_construction=true） |
| `_execute_policy(id, entities)` | 脱水/浸泡切换；应急定量配给启用/结束 |
| `update_cooldowns(dt, time_scale)` | 游戏天数衰减冷却计时器 |
| `get_state() / load_state()` | 当前状态 + 冷却列表 + 建筑 ID 自增值 |

**脱水效果**: 食物消耗 ×0.2 / 非豁免建筑产出 ×0.1 / 科研 ×0.1 / 库存与暴露人口按区域环境连续累计损耗；脱水时按“闲置→生育→建筑倒序”撤岗

**配给效果**: 食物消耗 ×0.75、建筑与科研效率 ×0.9，并按游戏日缓慢降低健康和安定度。没有班次、维护和事故模型前不提供抽象全国增产倍率；没有年龄/育儿/住房模型前不提供抽象生育倍率。

## 场景脚本功能说明

### scenes/main.gd
入口场景，`_ready()` 中 `call_deferred` 跳转到 `initial_menu.tscn`。

### scenes/main_menu/initial_menu.gd
标题画面。3 个按钮 → StartGameMenu / SettingsScreen / quit()。使用 `$MainVBox/ButtonName` 路径引用节点。

### scenes/main_menu/start_game_menu.gd
开始菜单包含 4 种 State（MAIN / NAMING / DIFFICULTY / GUIDANCE）：
- **MAIN**: 新游戏 / 继续游戏（找最新存档） / 加载存档 / 返回
- **NAMING**: 校验宇宙名；**DIFFICULTY** 固化场景快照；**GUIDANCE** 选择完整/精简/关闭模式。
- 确认后调用 `GameState.new_game(...)`，写入首都未定的“初始存档”，再进入 MainScreen。
- “加载存档”打开共享 `SaveBrowser`，收到 `save_selected(filepath)` 后统一调用 `SaveManager.load_game()`。

MainScreen 在 `capital_zone_id=-1` 时显示首都候选层并锁定第 0 天；确认后才开放普通暂停、导航和模拟推进。

### scenes/shared/save_browser.gd
主菜单与暂停菜单复用的全屏存档浏览器。扫描 `res://saves/` 后按宇宙分组，将每个存档生成为真实 `Button` 卡片，直接显示名称、天数和保存时间；支持单击选择、双击加载、Enter 加载、Delete 删除与 Esc 返回。工具栏可删除选中的单个存档，分组标题可删除整个宇宙，两者都在覆盖层中二次确认。

### scenes/main_menu/settings_screen.gd
4 个标签页（游戏/显示/音频/控制），通过代码动态构建 `HSlider` + `SpinBox` + `CheckBox` 控件。`_load_settings()` 从 `res://settings.json` 读取，`_save_settings()` 写入并应用全屏/vsync。游戏页以 `auto_save_interval_days` 保存 1–10000 天的自动存档间隔，默认 100 天；同页包含开发者模式开关，应用后同步到 `GameState`。

游戏页只读取当前的三态默认引导 `guidance_mode` 和按游戏日计算的 `auto_save_interval_days`；不将历史教程键或现实分钟自动保存键当作兼容输入。

### scenes/game/main_screen.gd
游戏主界面，最关键的 UI 脚本：
- `_ready()`: 若 `GameState.game_started == false` 则创建默认宇宙；连接状态刷新信号
- 模拟更新由 Autoload `GameState._process()` 持续驱动，切换子界面不会停止
- `_refresh_panels()`: 响应 `GameState.state_updated` 信号 → 重建资源面板（按组分）/ 文明面板（人口+科研）/ 环境面板（温度+辐射+光照+天数+时间倍率）
- 顶部自适应工具栏: 暂停 / `1x→2x→3x→5x` 四段 HSlider（含当前倍率文本）/ 科技树 / 政策 / 区域 / 星图；星图开局显示为锁定，望远镜科技解锁；开发者模式可绕过入口限制
- 知识政策不在主工具栏重复设置入口；从知识图工具栏进入，并返回知识图
- 开发者工具面板: 动态表单修改人口、库存人口、生育人口、7 类资源和 3 类科研点，并提供资源填充、全科技解锁动作
- `_input()`: 只处理开发者/引导弹层关闭与 `+/-/1/2/3/5` 调速；空格和非弹层 `Esc` 由 `GlobalInputRouter` 统一处理

### scenes/game/game_menu.gd
暂停菜单。5 个按钮通过 `%UniqueName` 绑定 → 继续 / 保存 / 加载 / 设置 / 主菜单。居中卡片使用明确标题、副标题、独立保存状态面板与底部提示；“保存”打开命名弹层，预填“宇宙名_Day天数”并列出最近三个存档；“加载”在当前场景中打开与主菜单完全相同的 `SaveBrowser`；弹层内 `Esc` 优先关闭，菜单内 `Esc` 恢复模拟。

所有主要菜单与游戏子界面以 1920×1080 逻辑画布布局，配合 `canvas_items`/`keep` 拉伸策略适配 1080p、2.5K 及更高常规分辨率。顶部工具栏统一 24px 安全边距，底部提示使用 16px 高对比文字；区域地图和详情继续由 `HSplitContainer` 隔离并裁剪。
