# 架构与真实性审查

审查日期：2026-07-25  
经营玩法补充审查：2026-07-27
范围：当前 Godot 模拟层、游戏内决策界面、区域经济、知识系统、存档边界与 `f1519e9` 旧版行为参考。

## 1. 决策设计判据

玩家应控制现实中的**命令、制度、预算、岗位、优先级和预案**，不能直接控制结果。每项可点击策略至少回答：

1. 谁有权执行，当前文明是否具备该组织能力；
2. 在哪个区域执行，占用哪些真实人员、设施、材料、空间和能源；
3. 实施需要多久，运行后需要多少维护；
4. 通过什么因果链影响产出、健康、知识或风险；
5. 有哪些机会成本、副作用、失败条件和撤销代价；
6. 决策者当时掌握哪些信息，哪些结果仍不确定。

因此，合理控制包括“把已掌握课程以师徒制进行重点培养”“降低统一口粮标准”“建立档案校对岗位”；不合理控制包括“知识保留率 +30%”“全国生产 ×2.5”“支付一次食物后永久三倍生育”“直接指定灾害伤亡”。

## 3. 待修正问题

### P0：会破坏核心因果或物理守恒

1. **区域经济仍以全局结算、事后分账为主。** `EntityManager` 先对文明总账生产和消费，`RegionalLogisticsSystem.reconcile_after_simulation()` 再按产出率分配增量、按区域编号扣减消耗。远区建筑的燃料、食物和材料并未逐笔从当地库存或运输网络支付。应改为逐区域事务结算，文明总账只由地方库存与在途库存求和。

2. **电力把功率和储能混为同一资源。** 建筑使用 kW 产出/需求，但 `electricity.amount` 又像可存库存一样写入“发电减用电”的余额。应拆分即时功率平衡（kW）和储能（kWh），并按区域电网、线路容量、损耗和孤网分别结算。

3. **施工岗位和运行岗位仍是同一容量。** 首轮已消除 `worker_capacity == 0` 自动完工，并为庇护所、仓库、屏蔽站补入实际人员；但当前同一 `assigned_workers` 同时代表施工队和完工后的运行人员。仍需拆成施工任务、运行班组和维护班组。

4. **原始文明开局资源与知识链冲突。** 当前文明只掌握石木工具和火，却拥有成品铁库存，并能在无冶金能力时建设铁矿场。需要重新定义开局物资含义，增加石材、木材、黏土等早期建材，并让采矿、选矿、冶炼和金属施工形成连续链。

5. **存档读取尚非完整事务。** `GameState.from_dict()` 会在所有子系统验证完毕前逐步覆盖运行状态，多个子系统也未统一严格校验 `state_version`。应先解析到临时状态树、完成版本/引用/守恒校验，再一次性提交，保证失败不改变当前游戏。

6. **人口暴露已统一第一阶段，但对象范围尚不完整。** 活动人口现按区域温度、辐射和运行庇护容量结算，脱水人口按运行仓体所在区域结算，饥饿与暴露均可归零并触发文明失败。迁徙途中人口、独立空气/水、设施维护故障及年龄/健康人口组仍未进入同一账本。

7. **危险事务已有纵向切片，但资源锁定仍不完整。** 当前公开预测、响应优先级、活动危机 ID、单次结果、区域人口/设施/知识损失和事件报告已经贯通并存档；预案尚未实体化教师、档案批次、样机、运输、口粮和能源预留，也没有灾后恢复队列。

### P1：不会立刻破坏守恒，但显著削弱“硬核真实”

1. **教学、研究和工程岗位没有区域归属。** `external_reserved_workers` 是全局整数；人员可被全局扣除，却没有来源聚落、通勤或迁移。应建立区域劳动力账本，项目绑定人员组和设施所在区域。

2. **“有教师”仍由文明全局掌握状态代替。** 只要节点为 `MASTERED/APPLIED`，任意闲置人口都可被系统推导为教师。需要人口组的知识熟练度、教师资格、年龄/健康和断层状态。

3. **保存优先级已经可结算，但知识载体仍是聚合量。** UI 不再接受虚构人数、档案体积和样机质量，改读实际运行庇护容量并提交可锁定的响应姿态；教师、档案批次、样机和工具尚未实体化，因此知识保护仍由姿态生成聚合系数。

4. **人口模型缺少年龄结构与家庭约束。** 当前生育岗位和自然增长是聚合倍率，没有孕产、婴幼儿抚养、住房、医疗、年龄结构和抚养比。未来人口政策必须作用于这些输入，不能恢复抽象增长 Buff。

5. **健康与社会安定是全球单值。** 区域灾害、配给、劳役和医疗无法产生地区差异、迁徙压力或政治执行成本。应先按聚落结算，再汇总文明指标。

6. **知识系统与旧技术效果后端仍可能形成双权威。** 当前通过显式映射把知识能力写入 `TechTree`，但部分调用方仍直接查询旧科技解锁状态。应把后端收缩为无研究状态的 `CapabilityRegistry`，所有玩法只查询一处能力事实。

7. **气候模型含明确的经验项。** 辐射使用 `distance^2.5` 衰减，氮氧相变使用固定一大气压阈值；文档已披露，但 UI 与变量命名仍应区分物理量和玩法危险度。扩展前需先验证经验项对可玩结果的必要性。

8. **水、维护和故障链缺失。** 聚落生存只显式结算食物，设施没有常规维护、备件、人员技能与随机故障。它们应在扩展生产种类前优先进入最小闭环。

### P2：表现与可解释性

1. 建筑地表仍是标签卡，不表达规模、施工人员、损毁部位和基础设施连接。
2. 当前假设全行星即时通信，玩家可跨区即时下令；设计文档已将其标为开发期简化，后续需由通信能力决定命令延迟和信息新鲜度。
3. 政策和生产效果需要统一的“本日变化来源”明细，避免玩家只能从总量反推因果。

## 4. 推荐实施顺序

1. 统一活动、庇护、迁移与脱水人口的区域暴露、保护和文明失败结算；
2. 建立危险预测、预案承诺、资源锁定、单次真实结算与灾后复盘事务；
3. 建立逐区域资源/功率事务和派生文明总账；
4. 拆分施工劳动与运行岗位，补齐原始材料链；
5. 建立区域人员组与项目岗位归属；
6. 实体化教师、档案、样机与避难方案确认；
7. 将旧 `TechTree` 后端收缩为单一能力注册表；
8. 最后扩展年龄结构、区域社会状态、水、维护故障和通信延迟。

在前六项完成前，不应继续增加新的免费倍率政策或更多装饰性资源。每个新系统都应先通过“来源—位置—占用—时滞—副作用—信息边界”验收。经营体验目标和阶段验收见[经营玩法审查与改造路线](经营玩法审查与改造路线.md)。
