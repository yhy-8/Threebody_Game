# 重构迁移方案：Python/Pygame → Godot 4

> **目标引擎**: Godot 4.4+
> **脚本语言**: GDScript（主）/ C#（性能关键模块可选）
> **迁移策略**: 完全重写，保留现有设计文档和游戏机制设计

---

## 一、Why Godot 4

| 维度 | 当前(Pygame) | Godot 4 |
|------|-------------|---------|
| 3D渲染 | 手写CPU透视投影 | GPU加速，内置PBR/后处理/粒子 |
| UI系统 | 自绘Button/Label/Panel | 原生Control节点，Layout/Theme系统 |
| 场景管理 | 手动状态机 | Scene + Node树，内置切换 |
| 输入处理 | Pygame事件循环 | Input系统 + Signal机制 |
| 存档 | 手写JSON | FileAccess + Resource序列化 |
| 资源管理 | 无 | Resource系统，支持preload/引用 |
| 调试 | print | 内置Debugger + Profiler |
| 打包发布 | pyinstaller | 一键导出Win/Mac/Linux/Web |

核心论点：这个游戏是 **2D UI重型 + 3D场景混合** 的管理模拟游戏，正好是Godot最强的领域。

## 四、关键设计决策

### 4.1 为什么选GDScript而非C#
- GDScript语法接近Python，现有设计思路直接映射
- 模拟经营游戏不瓶颈在脚本语言
- 开发迭代速度快，无需编译
- 如果后续发现性能热点（如72区循环），可局部改C#/GDNative

### 4.2 UI架构：Control节点 vs 3D中画UI
- 主界面(HUD/面板)：使用Godot **Control节点**（2D）
- 3D星图：使用 **SubViewport** 嵌入3D场景
- 理由：Godot的Control节点支持锚点/容器/主题/响应式布局，比在3D中画UI合理得多

### 4.3 资源表示：Resource子类化
建筑、科技、资源定义全部用Godot的 `Resource` 子类：
```gdscript
# building_definition.gd
class_name BuildingDefinition extends Resource
@export var building_id: String
@export var display_name: String
@export var resource_cost: Dictionary
@export var worker_capacity: int
@export var per_worker_output: Dictionary
# ...
```
优势：编辑器中可直接编辑.tres文件，替代config.yaml，可视化配置纠错。

### 4.4 存档系统
- 使用Godot `ResourceSaver` / `ResourceLoader` 保存为 `.tres`（文本格式，可读可diff）
- 或自定义JSON序列化（保留现有格式兼容性）

## 六、VSCode开发环境配置

### Godot + VSCode 工作流

1. **安装Godot 4.4+** （从 godotengine.org 下载）
2. **VSCode插件**：
   - `godot-tools` — 语法高亮、调试、场景运行
   - `gdscript` 或 `godot-vscode` — GDScript语言服务
3. **Godot编辑器设置**：
   - 编辑器 → 文本编辑器 → 外部 → 使用外部编辑器 → VSCode
   - 这样双击脚本在VSCode中打开
4. **工作流**：
   - 场景搭建、资源编辑：在Godot编辑器中进行
   - 脚本编写、调试：在VSCode中进行
   - 运行：F5（Godot编辑器）或终端 `godot --path .`

### 版本控制注意
- `project.godot` 和 `.tscn` 文件均为文本格式，适合git追踪
- `.uid` 文件需要提交（资源唯一标识符）
- `*.import` 文件由Godot自动生成，需要提交
- `.godot/` 目录可忽略
