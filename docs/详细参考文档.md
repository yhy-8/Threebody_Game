## 1. scripts/simulation/three_body.gd — 三体运动模拟

`class_name ThreeBodySimulation extends RefCounted`

### 常量

| 名称 | 值 | 说明 |
|---|---|---|
| `G` | 1.0 | 简化引力常数 |
| `TRAIL_LENGTH` | 200 | 每颗星的轨迹队列长度 |

### 属性

| 名称 | 类型 | 说明 |
|---|---|---|
| `stars` | Array[StarData] | 4 天体（3 恒星 + 1 行星） |
| `time_scale` | float | 模拟时间倍率（默认 1.0） |

### class StarData

| 字段 | 类型 | 说明 |
|---|---|---|
| `mass` | float | 质量（恒星 500~1100，行星 1.0） |
| `position` | Vector3 | 当前 3D 坐标 |
| `velocity` | Vector3 | 当前速度 |
| `color` | Color | 显示颜色 |
| `radius` | float | 显示半径（缩放 0.5 后使用） |
| `is_planet` | bool | 是否为行星 |
| `trail` | Array[Vector3] | 轨迹队列（FIFO，max 200） |

### 方法

| 方法 | 参数 | 返回值 | 功能 | 调用方 |
|---|---|---|---|---|
| `_init()` | — | — | 调用 `_initialize_stars()` 生成初始配置 | GameState.new_game, GameState.from_dict |
| `_initialize_stars()` | — | — | 随机生成层级稳定 4 天体：内双星（互绕）+ 外第三星（绕双星质心）+ 行星（绕双星） | `_init()` |
| `compute_forces_for_state(positions)` | Array[Vector3] | Array[Vector3] | 遍历所有星对计算引力合力 = `G×mi×mj×r / dist^3`（用于 RK4 四步） | `update()` ×4 |
| `update(dt)` | float | void | RK4 四阶积分 + 1e-5 随机微扰 + 轨迹 push/pop | GameState.update |
| `has_collision()` | — | bool | 任意两天体中心距小于半径和时返回 true | GameState.update |
| `get_environment_params()` | — | Dictionary | 返回 {light_intensity, heat_level, temperature, radiation, stability} — 光照=Σ mass×10/(dist²+100)/8，温度=-273.15+光照×7000，辐射=Σ mass×200/dist^2.5，稳定性=1/(1+accel/0.1) | GameState.update, PlanetZoneManager |
| `_compute_stability(planet)` | StarData | float(0~1) | 行星所受合力加速度的倒数映射 | `get_environment_params()` |
| `get_stars_data()` | — | Array[Dictionary] | 每星 {position, mass, is_planet} | GameState.update, PlanetZoneManager |
| `get_planet_position()` | — | Vector3 | 行星坐标（遍历找 is_planet==true） | GameState.update |

| `get_all_zones_summary()` | — | Array[Dictionary] | 144 区模拟层简要数据，加入 air_temp / atmosphere / atmosphere_state | GameState.get_state |

核心字段：`zone_id`、`local_up`、`local_east`、`local_north`、`ground_visual_root`、`building_visual_root`。

拟议方法：

- `set_observed_zone(zone_id)`：校验 `0~143`，并要求首都确认后目标处于当前实时可见区，再计算区域中心地平坐标并刷新地面。

- `get_body_altitude_azimuth(body_id)`：供测试验证不同区域的天体高度角/方位角。

坐标契约：`altitude = asin(dot(direction, local_up))`；高度角 `<= 0` 的天体被地面遮挡。方位角需使用 `east/north` 投影和 `atan2`，并在文档/测试中固定零度方向。

### 11.4 `DiscoverySystem` 与随机事件契约

所有发现来源标准化为 `DiscoveryContribution`：

```gdscript
{
	"source_id": "event:comet_00042",
	"source_type": "event", # observation/experiment/production/event/ruin
	"target_node_id": "celestial_motion",
	"clue_strength": 0.25,
	"evidence": {"long_period_observation": 12.0},
	"tags": ["astronomy", "one_time"],

```

随机事件、遗迹、生产和区域环境只提交贡献；`DiscoverySystem` 校验来源、转交 `KnowledgeSystem` 并记录结果。事件不得直接设置 `node.state`、研究进度、能力标签或 UI 可见性。

需要预留的发现入口：

- `record_observation(observer_id, phenomenon_id, measurement, quality)`
- `record_experiment(experiment_id, result, reproducibility)`
- `record_production_experience(building_id, process_id, amount)`
- `resolve_event_discovery(event_id, choices, outcome)`
- `analyze_ruin_artifact(artifact_id, analysis_method, facility_id)`

### 11.5 研究、工程化与传承项目

`ResearchProjectSystem` 保存人员分配、设施要求、材料、进度和暂停原因；其 `PROGRESS_MULTIPLIER=0.5`，研究日工作量为 `(对应机构吞吐量 + workers×0.04) × 0.5`，`get_project_views()` 使用同一公式返回实际 `daily_rate` 和 `eta_days`。`EngineeringProjectSystem` 与理论研究分离，保存样机、测试、工艺成熟度和已授予能力标签，不使用该研究倍率。二者当前状态版本为 2：未完成项目即使暂停也占用项目槽，暂停只释放人员；项目视图提供进度、实际工作速率和预计完成天数，调员与恢复前重新校验闲置人口。失败/事故与设施独占仍是后续扩展。

`KnowledgeInheritance` 按游戏世代而非渲染帧结算，输入至少包括人口年龄/死亡、教师和学徒、教育覆盖、记录副本及其区域、知识机构耐久、相关工艺运行时长、灾难损失，以及 `EducationSystem` 和 `PreservationAllocator` 已结算的实际结果。输出为标准化 `KnowledgeShock/RetentionResult`，再由 `KnowledgeSystem` 决定是否进入 `DEGRADED`。它不能直接读取 UI 滑条，也不能把政策权重当成知识值。

#### 11.6.2 `EducationSystem`

`EducationSystem` 不拥有独立人口池。教师和学生必须是 `EntityManager`/未来人口子系统中的实际人口分配，教学时间与生产、研究和建造工时竞争。

当前知识政策 UI 不直接要求玩家填写师生人数和课时。玩家选择已掌握且标为可传授的课程、当前能力允许并适合该课程传承结构的组织方式，以及维持/常规/重点/危机投入级别。`EducationSystem` 根据闲置人口、师生比、设施和投入级别生成 `TeachingPlan`，并预览实际占用人数、授课人时与离散整日岗位的生产机会成本。UI 不能构造或覆盖这些规则。

`TeachingPlan` 建议结构：

```gdscript
{
	"plan_id": "plan:basic_literacy_001",
	"curriculum_id": "basic_literacy",
	"teacher_ids": [],
	"student_group_ids": [],
	"hours_per_day": 4.0,
	"material_allocation": {},
	"facility_ids": [],
	"practice_building_ids": [],
	"emergency_course": false,
}
```

当前接口：

- `validate_plan(plan)`：检查教师是否掌握课程、人口是否重复占岗、教材/场地/实践设施是否可用。
- `start_plan(plan)` / `toggle_pause_plan(plan_id, entities)` / `cancel_plan(plan_id)`：管理持续教学计划；恢复时重新校验闲置人口和绑定设施。
- `update_day(context)`：按教师掌握度、师生比、课时、识字/语言、教材、场地和实践条件输出 `TeachingResult`。
- `preview_plan(plan)`：返回占用工时、覆盖人数、预计活态传承和生产机会成本，不提前结算。
- `get_reserved_workers()` / `get_running_workers()`：分别返回仍在等待或授课的占岗人口，以及设施可用且本步真正产生教学覆盖的人口。
- `get_state()` / `load_state(data)`：保存教师、学生、课程、进度和暂停原因。

纯文献学习最多恢复记录可表达的部分；节点的 `inheritance_profile` 标记需要隐性工艺时，缺少教师示范或实践设施不得恢复完整 `practice_level`。抢救式课程提高短期覆盖，但结果应带有深度上限、疲劳与生产停顿。

#### 11.6.3 `PreservationAllocator`

避难容量不得压缩成单一人数。设施快照至少提供：

```gdscript
{
	"shelter_id": "building:deep_shelter_012",
	"usable_volume_m3": 0.0,
	"berths": 0,
	"life_support_people": 0,
	"food_water_person_days": 0.0,
	"dry_archive_volume_m3": 0.0,
	"heavy_storage_mass_kg": 0.0,
	"continuous_power_kw": 0.0,
	"environment_control_level": 0.0,
}
```

`PreservationPlan` 保存候选人口组、教师/专家、学徒、档案批次、样机/模具/关键工具、领域/载体权重、手动锁定项和应急姿态。人员始终只占一个人口名额；教师身份作为该人员的知识属性参与收益计算，不能另生成“教师单位”。

拟议接口：

| 方法 | 功能 |
|---|---|
| `preview_plan(plan, shelters, forecast_snapshot)` | 返回确定的容量占用/未安置对象，并且只在预测快照允许时附加伤亡区间与知识衰退风险 |
| `validate_plan(plan, shelters)` | 检查人员重复、对象不存在、容量维度、供电及手动锁定冲突 |
| `commit_plan(plan_id)` | 冻结已确认方案，供灾害结算读取；不得在此时直接杀伤人口或知识 |
| `resolve_plan(plan_id, hazard_outcome)` | 依据同一灾害结果生成实际 `PreservationResult`，禁止再次随机抽取灾害强度 |
| `get_state()` / `load_state(data)` | 保存方案、档案/样机位置、确认状态和已结算来源 ID |

`forecast_snapshot` 只能由 `HazardForecastService` 产生，且允许为 null。`PreservationAllocator` 不得读取 `ScenarioManager` 的未来位置、场景种子或真实灾害强度来补齐未知字段。null/低层级预测下仍返回确定的装载事实，但 `estimated_casualties`、`affected_zone_ids`、`knowledge_degradation_probability` 等字段必须缺失或明确为未知，不能填入内部真值后仅在视觉上遮挡。

`PreservationResult` 至少返回幸存人口 ID/分组、幸存教师与学徒、幸存档案批次、幸存实物、各容量实际占用、未安置对象、实际伤亡和面向 `KnowledgeInheritance` 的损失向量。结果必须由给定方案与已经发生的 `HazardOutcome` 确定性复现；实际结果与此前预测不同属于正常玩法结果。

#### 11.6.4 UI 与验收约束

- 知识政策页只实例化当前能力已经允许的制度、载体、已显露领域、教学方式和保存操作。未满足能力前置的内容不占位、不显示未来名称，也不生成禁用滑杆。
- 未被真实自动分配器消费的总体/载体/领域权重不得显示；未来重新引入时必须同时展示权重生成的实际对象清单、容量占用和未纳入项。
- 教学入口为课程目标、组织方式和宏观强度；师生数、每日课时与工时损失只作为系统推导的事实预览，不能重新暴露成日常微操表单。口述、记录辅助、固定课程与专业院校方式分别由能力及实际运行设施解锁。
- 没有可用避难设施时整个保存区隐藏。危机预览只显示当前载体能力确实存在的装载维度；伤亡、受灾区域和知识降级按预测层级逐项出现，尚无对应预测字段时不显示该结果行。
- 已显示的危机预览需列出已纳入/未纳入人口、其中教师/专家与学徒、当前可用载体和各容量瓶颈；不得把“纳入避难方案”直接标成“必定获救”。
- 相同人员不能同时作为普通人口和教师占用两个床位；纸质档案不能消耗生命保障名额，但必须消耗真实干燥体积和环境控制。
- “知识优先”不能突破容量或提供知识加成，只改变短缺时的选择顺序；“生命优先”也不能自动保留无人掌握且无记录的知识。
- 仅保存文献、仅保存教师、同时保存教师和可实践样机三种方案应产生不同且可测试的传承结果。
- 当前存档必须包含避难所容量、人口与政策状态；缺失时拒绝加载，不由读取器猜测默认状态。
- 测试需保证低预测状态下预览字典本身不含真实伤亡/轨道字段；不能只测试控件隐藏。对同一预测快照切换不同方案时，只能改变由方案本身可推导的暴露和容量信息。

### 11.7 场景难度配置、`ScenarioManager` 与轨道阶段

#### 11.7.1 `ScenarioDifficultyConfig`（开发期数据资源）

实际文件：

- `resources/configs/difficulty_preset.gd`：`class_name DifficultyPreset extends Resource`
- `resources/configs/scenario_difficulty_config.gd`：`class_name ScenarioDifficultyConfig extends Resource`
- `resources/configs/scenario_difficulties.tres`：运行时唯一难度预设数据

这组资源是随项目提交、供开发者和平衡人员编辑的开局规则数据，不属于 `res://settings.json`，也不出现在游戏内开发者模式。`.tres` 可通过 Godot Inspector 或文本修改；运行时不要求热重载，重新启动项目或测试后生效。

`DifficultyPreset` 当前字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | StringName | 不可变存档 ID，例如 `easy/normal/hard/extreme` |
| `display_name` | String | 菜单显示名称，随配置资源维护 |
| `description` | String | 菜单说明，随配置资源维护 |
| `stable_years` | float | 进入混沌前的游戏年数，必须为有限且非负数 |
| `sort_order` | int | 新游戏菜单顺序 |
| `selectable` | bool | 是否作为标准难度显示 |

`ScenarioDifficultyConfig` 当前字段：

| 字段 | 类型 | 默认设计值 | 说明 |
|---|---|---:|---|
| `config_version` | int | 1 | 写入新场景快照，配置语义改变时递增 |
| `default_preset_id` | StringName | `normal` | 新游戏默认选项，必须引用现有可选预设 |
| `presets` | Array[DifficultyPreset] | easy/normal/hard/extreme | 标准难度目录，ID 不得重复 |

当前接口：

| 方法 | 参数 | 返回值 | 约束 |

`create_snapshot()` 输出至少包含：

```gdscript
{
	"difficulty_config_version": 1,
	"difficulty_id": "normal",
	"stable_years": 50.0,
	"days_per_year": 365.0,
	"chaos_start_day": 18250.0,
```

#### 11.7.2 `ScenarioManager`

当前阶段常量：

```gdscript
const STABLE_EPHEMERIS := "STABLE_EPHEMERIS"
const CHAOTIC_NBODY := "CHAOTIC_NBODY"
```

核心状态：

| 字段 | 类型 | 说明 |
|---|---|---|
| `difficulty_id` | String | easy/normal/hard/extreme/custom |
| `difficulty_config_version` | int | 创建宇宙时采用的难度配置版本 |
| `stable_years` | float | 规则指定的安全发展年数 |
| `days_per_year` | float | 创建时固化的游戏年换算 |
| `chaos_start_day` | float | `stable_years * days_per_year`，创建时计算并固化 |

| `ephemeris_state` | Dictionary | 规定星历参数和版本 |
| `chaos_started` | bool | 防止重复转换/事件 |
| `actual_transition_day` | float | 实际转换帧的游戏时间 |

当前方法：

| 方法 | 功能 |
|---|---|
| `create_scenario(difficulty_snapshot, seed, environment)` | 接收已校验且可序列化的预设快照，生成稳定星历并绑定现有 N 体模拟器 |

`ScenarioManager` 不持有标准难度映射，也不在加载存档时重新查询全局难度资源。配置修改只影响之后创建的宇宙；当前存档使用自身固化的 `stable_years/days_per_year/chaos_start_day`。没有完整 `scenario` 的文件不属于当前格式并直接拒绝。

配置测试至少覆盖：资源可加载、所有 ID 唯一、默认 ID 可选、年份有限且非负、自定义范围有效、`create_snapshot()` 换算正确；另以修改后的临时资源创建新场景，并验证修改前存档的倒计时保持不变。

### 11.8 观测与卫星网络

轨道预测的当前输入不再只是科技布尔值：

```gdscript
prediction_capability = f(
	theory_capability,
	observation_data_quality,
	time_baseline,
	spatial_coverage,
	compute_capacity,
	instrument_calibration,
)
```

`ObservationNetwork` 当前保存实际运行观测站数量、观测基线、校准度、数据质量、版本和最新公开测量；未供电、未分配人员或仍在施工的天文观测站不贡献质量。`SatelliteNetwork` 保存卫星传感器质量、在线状态和合并覆盖率，提供 `deploy_satellite()` 与 `set_online()`；发射与维护玩法要等火箭系统接入，当前不会自动生成卫星。

#### 11.8.1 `HazardForecastService`

实际文件：`scripts/simulation/hazard_forecast_service.gd`。职责是生成文明当下能够知道的危机预测，不负责推进真实轨道，也不负责灾害结算。

当前预测层级：

```gdscript
enum ForecastLevel {
	NONE,
	QUALITATIVE_WARNING,
	REGIONAL_RISK,
	QUANTITATIVE_IMPACT,
	HIGH_PRECISION_PROBABILISTIC,
}
```

层级上限由知识能力标签控制：

- `hazard_warning`：允许定性预警。
- `regional_hazard_projection`：允许公布可能受灾区域和宽时间窗。
- `casualty_estimation`：允许结合人口、避难所和建筑脆弱性给出伤亡区间。
- `knowledge_loss_projection`：允许结合教师、档案、样机和节点传承状态给出退化风险。

标签是必要条件而非完整结果。实际层级和置信度还读取观测时间跨度、测量误差、仪器校准、卫星覆盖、计算能力、环境模型，以及人口/建筑/档案数据完整度。理论解锁但没有数据时，应返回较低层级或更宽区间。

`HazardForecastSnapshot` 当前结构示例：

```gdscript
{
	"forecast_id": "forecast:00042",
	"generated_game_day": 1200.0,
	"source_observation_version": 18,
	"model_capability_version": 4,
	"level": ForecastLevel.REGIONAL_RISK,
	"confidence": 0.32,
	"valid_until_game_day": 1230.0,
	"known_fields": ["risk_trend", "time_window", "possible_zone_ids"],
	"risk_trend": "rising",
	"time_window": {"earliest": 1220.0, "latest": 1300.0},
	"possible_zone_ids": [12, 13, 24],
	"scenario_ranges": [],
	"assumptions": [],
}
```

未解锁字段不写入快照。达到更高层级时才可增加 `casualty_range`、`knowledge_loss_ranges`、区域危害强度分布等内容；所有数值预测必须附带范围、置信度、生成时间和主要假设。

当前接口：

| 方法 | 功能 |
|---|---|
| `build_forecast(game_day, capabilities, observation_data, infrastructure, census_snapshot)` | 仅用文明可访问输入生成新预测快照 |
| `get_public_snapshot()` | 返回已经按能力裁剪的不可变快照，供危机 UI 和保存分配器使用 |
| `is_stale(game_day, observation_version, satellite_version)` | 判断观测、基础设施版本或有效期变化是否使预测过期，并标记当前快照 |
| `compare_plans(plans, forecast_snapshot)` | 在同一公开预测分布下比较方案；不访问真实未来 |
| `get_state()` / `load_state(data)` | 保存预测来源、层级、区间、置信度和失效状态 |

禁止依赖：`ScenarioManager` 的未来天体快照、规定星历未来段、场景种子、尚未发生的 `HazardOutcome`。预测服务只可接收观测系统公开的历史/当前测量；模拟真值即使已经在内存中，也不能作为文明预测输入。

规则 HUD 的 `chaos_start_day` 与 `HazardForecastSnapshot` 是两套信息。前者是难度承诺，可以告诉玩家安全窗口何时结束；后者是文明科学认知，决定是否知道恒星轨迹、受灾区域和伤亡。两者必须使用不同字段和 UI 标签。

`tests/scenario_progression_test.tscn` 已覆盖：

- `NONE` 层输出不包含区域、伤亡或知识损失字段。
- 只有理论、没有观测数据时不能越级生成定量结果。
- 增加观测基线、校准和卫星覆盖后，允许提升层级或收窄区间。
- 相同公开输入生成可复现预测；真实场景种子不同但观测尚不可区分时，公开快照不得泄露差异。
- 预测与实际 `HazardOutcome` 可以不一致，灾害结算仍只执行一次真实结果。

#### 11.8.2 `EnvironmentalHazardSystem`

实际文件：`scripts/simulation/environmental_hazard_system.gd`。它只读取当前已经发生的区域温度、辐射、人口位置和设施运行状态，负责活动人口暴露、响应预案、活动危机和单次完成报告；禁止读取未来轨道或用 `HazardForecastSnapshot` 作为真实伤害输入。

当前公开响应姿态为：

- `population`：100% 运行庇护容量用于人口，知识载体保护最低；
- `balanced`：78% 容量用于人口，其余空间形成中等知识保护；
- `knowledge`：55% 容量用于人口，知识重建保护最高。

以上是第一阶段聚合模型。设施容量必须来自 `EntityManager.get_zone_shelter_status()`，只计已完工、未损毁、已配员且本模拟步实际运行的庇护所；知识空间尚未拆成教师、档案批次和样机实体。

主要接口：

| 方法 | 功能 |
|---|---|
| `commit_response_plan(priority, game_day, forecast, entities, settlement)` | 记录公开预测 ID、响应优先级和提交时容量；活动危机中拒绝修改 |
| `begin_step(...)` | 从当前有人区域评估严寒、高温和辐射，必要时建立稳定危机 ID |
| `get_workforce_multiplier(...)` | 把进入避险流程的人口转为非维生生产机会成本 |
| `process_population_exposure(...)` | 按区域人口、保护容量和当前环境累计并写回实际死亡 |
| `end_step(...)` / `force_resolve(...)` | 安静期结束或文明终结时生成唯一实际报告 |
| `get_state()` / `load_state(data)` | 严格保存预案、活动危机、损失小数余量和完成报告 |

`GameState` 在报告完成后把 `knowledge_loss_vector` 交给 `KnowledgeInheritance.apply_disaster_result()`，再记录实际死亡、设施损毁与退化节点数。`tests/hazard_gameplay_test.tscn` 覆盖无保护伤亡、运行庇护差异、危机中预案锁定、单次报告、人口归零与存档往返。

### 11.9 起始定居、开局引导与跨区系统（核心闭环已实现）

#### 11.9.1 `OpeningGuidanceController`

实现文件：`scripts/guidance/opening_guidance_controller.gd`。该类维护可序列化引导状态，不持有模拟真值，不直接操作人口、资源、科技、建筑或轨道。

现有枚举：

```gdscript
enum GuidanceMode { FULL, COMPACT, OFF }
enum OpeningPhase {
	AWAITING_CAPITAL,
	RULES_TIME,
	FOOD_SECURITY,
	SURVIVAL,
	KNOWLEDGE,
	OBSERVATION,
	EXPLORATION,
	AUTONOMY,
	COMPLETE,
}
```

当前任务使用内置版本化定义；拆分为外部任务资源仍属于后续维护优化：

```gdscript
{
	"id": "opening:first_teaching_plan",
	"phase": OpeningPhase.KNOWLEDGE,
	"event": "teaching_plan_progressed",
	"target": "knowledge.teaching_plans",
```

核心状态：

```gdscript
{
	"guidance_version": 3,
	"mode": GuidanceMode.FULL,
	"phase": OpeningPhase.AWAITING_CAPITAL,
	"completed_task_ids": [],
	"skipped_task_ids": [],
	"dismissed_hint_ids": [],
	"deferred_task_reasons": {},
	"handbook_seen_concept_ids": [],
	"group_deferred": false,
	"group_deferred_reason": "",
}
```

现有接口：

| 方法 | 功能 |
|---|---|
| `initialize(mode, restored_state={})` | 创建或恢复内置版本化任务状态 |
| `handle_domain_event(event_id, payload)` | 根据真实领域结果完成任务；相同事件来源只处理一次 |
| `get_active_task_views()` | 按模式返回完整卡片、精简提示或空展示；不改变世界状态 |

#### 11.9.2 `CapitalSelectionService` 与区域认知

现有认知枚举：

```gdscript
enum ZoneKnowledgeLevel { UNKNOWN, OBSERVED, FAMILIAR, SURVEYED, MONITORED }
```

`ZoneKnowledgeView` 仅包含对应认知层允许公开的地形、当前环境、表面迹象、估算区间、置信度、更新时间和未知字段列表。它不得持有完整 `PlanetZone` 引用或隐藏字段副本。

`CapitalSelectionService` 现有接口：

| 方法 | 功能 |
|---|---|
| `build_candidate_views(public_zone_views, scenario_rules)` | 仅用公开数据产生候选理由、已知风险与未知项 |
| `rank_candidates(candidate_views)` | 返回可解释排序与置信度，不读取隐藏资源或未来轨道 |
| `validate_selection(zone_id, public_view)` | 检查候选有效性与当前可生存条件 |
| `confirm_capital(zone_id)` | 通过统一游戏命令设置首都，建立中心 `FAMILIAR` + 周围八格 `OBSERVED` 的连续 3×3 实时视野并发出 `capital_confirmed` |

未确认首都时 `GameState` 保持第 0 天和暂停标记；该暂停是开局流程状态，不受空格误解除。确认后恢复普通暂停控制，但仍保持暂停，玩家查看食物时限后主动开始推进。初始存档必须能保存 `capital_zone_id=-1` 并在读取后回到候选选择。

#### 11.9.3 `ExplorationSystem` 与 `RegionMovementSystem`

`RegionOperation` 已统一表示勘探、迁徙、运输和迁都；当前状态结构为：

```gdscript
{
	"operation_id": "region-op:000001",
	"type": "exploration",
	"population_count": 5,
	"origin_zone_id": 0,
	"destination_zone_id": 1,
	"route": [0, 1],
	"route_index": 0,
	"segment_progress_days": 0.0,
	"elapsed_days": 0.0,
	"cargo": {},
	"food_required": 0.8,
	"food_consumed": 0.0,
	"return_to_origin": true,
	"status": OperationStatus.TRAVELLING,
	"current_zone_id": 0,
}
```

`ExplorationSystem` 与 `SettlementSystem` 共同提供：

- `get_zone_knowledge(zone_id)`：返回裁剪后的不可变认知视图。
- `refresh_visibility(...)`：以每个有人区域的自身与周围八格生成 `visible_zone_ids`；覆盖消失时删除公开动态环境字段，但保留地形、资源估计、来源与 `knowledge_level` 历史。
- `can_plan_expedition(origin_zone_id, target_zone_id, ...)`：早期勘探只允许从有人口的已知区进入相邻目标。
- `complete_survey(operation, ...)`：实际抵达后提升认知层级，保存估算区间/来源/时间，不复制无限精度真值。
- `mark_knowledge_stale(zone_id, reason)`：环境、设施或时间变化后标记数据过期。

`RegionMovementSystem` 当前提供：

- `plan_route(origin, destination, ..., settlement_system, allow_unknown_destination)`：只在当前实时可见邻接图寻路；勘探仅允许最后一段进入未知目标。
- `start_operation(...)`：从出发区人口扣除当地建筑/生育岗位后校验实际闲置人口，再验证地方载荷和往返口粮并锁定人员/货物。
- `update(...)`：推进路线、消耗实际补给、在目标卸货/勘探并结算抵达与返程。
- `pause_operation(operation_id)` / `resume_operation(operation_id)`：暂停时不推进行程也不消耗口粮，并保存原行进/返程状态。
- `cancel_operation(operation_id)`：保留当前位置和已消耗资源；途中改道尚未实现。
- `get_state()` / `load_state(data)`：保存队伍、路线、进度、物资与状态。

人员到达前不得改变目标区可用人口；运输材料到达前不得计入目标区施工库存。环境风险结算读取当前实际环境，UI 计划只显示文明能够知道的风险。

当前迁移 UI 以所选实时可见区为目的地，允许从任一有人区域选择出发地并指定人数；除行程口粮外自动装载每人三日落地食物。道路等级、环境损毁、通信延迟与失联尚未进入运行模型；当前按全局即时指挥处理，后续边界以游戏设计文档第七章为准。

#### 11.9.4 `RegionalLogisticsSystem`

职责：在现有 `EntityManager` 文明总账之下维护区域库存归属、在途库存和道路/管线/电网三类独立连接。现有接口包括：

- `get_local_inventory(zone_id)`：只返回当地可用库存，不含运输中货物。
- `reserve_for_operation(...)` / `deliver_operation_resources(...)`：把货物从地方库存转为在途库存，并在实际抵达后卸货。
- `can_pay_local_cost(...)` / `commit_local_cost(...)`：建设只能消耗施工区域已有物资。
- `add_connection(...)` / `has_connection(...)`：分别维护道路、管线或电网，不使用全局连通布尔值。
- `get_state()` / `load_state(data)`：保存区域库存、在途预留与三类网络连接。

`EntityManager.resources` 是文明唯一总账，地方库存与在途库存是其空间分账；二者在生产/消耗后对账，不能分别领取或消费同一份资源。当前存档必须明确保存这些区域归属，不从全局状态推导默认聚落。

#### 11.9.5 `SettlementSystem` 前哨、聚落与迁都

- `is_zone_visible(zone_id)` / `refresh_visibility(...)`：提供人口驱动的公开动态信息边界；`visible_zone_ids` 是当前覆盖，不替代保存在每区记录中的历史认知等级。
- `refresh_settlement_status(...)`：从当地人口、已完工庇护、建筑实际食物产出、地方储备和通信能力更新补给状态。
- `get_outpost_upgrade_requirements(...)` / `upgrade_outpost(...)`：检查 5 人、庇护容量、日食物自给、7 天储备、可确认步行路线和符号记录能力，不把尚未实现的道路建设当作开局前置，也不使用固定建筑数上限。
- `complete_capital_relocation(target_zone_id, game_day)`：仅在迁都队实际到达后更换首都身份。`GameState.start_capital_relocation()` 负责检查常设聚落/档案能力并锁定 10 人、25 铁材与口粮；到达后将当前全局效率即时降至不高于 85% 作为协调损失。

当前补给状态使用真实地方分账和建筑运行记录，但尚未实现断供强制撤离、失联事件或独立水资源。

#### 11.9.6 UI 与验收约束

- 完整/精简/关闭模式共享同一模拟输入和结果；测试对相同操作序列比较最终 `GameState`，除引导状态外应一致。
- 控件高亮找不到语义目标时降级为文字说明并报告开发警告，不得崩溃或阻塞游戏。
- 改变隐藏矿藏/未来轨道但保持 `ZoneKnowledgeView` 相同时，候选区排序必须完全一致。
- 保存于 `AWAITING_CAPITAL`、任一引导阶段和进行中的勘探/迁徙任务后，读取应恢复同一阶段、路线进度和暂停规则。
- 跳过、恢复和重复领域事件不能重复扣除/增加人口、资源、知识或建筑。

### 11.10 开发期当前格式契约

当前唯一格式为 `schema_version=10`。它包含完整轨道/场景状态、144 区双层气候与大气相态、版本 2 知识图、版本 2 研究/工程项目、教学项目、知识制度筹建与维护岗位、历史区域认知与 `visible_zone_ids`、首都与区域分账、在途行动、探索、引导、观测网络、文明预测、环境危机/响应预案/完成报告、持久事件日志和文明终结原因；保存文档只写一份 `state`，校验和直接对应这份状态。

`GameState.validate_serialized_state()` 在任何 `reset()` 或字段覆盖之前检查精确 schema、必需区段和嵌套结构。`SaveManager.scan_saves()` 不展示不满足当前契约的文件，`load_game()` 再次验证并拒绝加载。开发期格式变化应直接提升 schema、更新序列化/校验/测试并重建测试存档，不实现历史版本阶梯、旧键别名、缺字段补建或双格式写入。

设置、配置资源和知识数据遵守相同原则：只有当前键与当前数据版本具有定义。正式发布前若确定兼容范围，再另行设计有限版本转换器；当前代码不得为假设中的未来兼容预留重复状态源。
